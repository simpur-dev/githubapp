> 原则：系统能力优先、不引第三方库；每项给出 API 名、版本、替代方案与收益。
> 兼容基线：compatibleSdkVersion 6.1.0(23) / targetSdkVersion 26.0.0。

## 2. 显式偏差决策（有据可查）

### 2.1 GraphQL（目标规格 vs 现实）

- **决策：REST 为主，GraphQL 预留不启用。**
- 依据：
  1. GitHub GraphQL 需要 PAT 勾选 GraphQL 权限域且通知/列表接口返回模型差异大，切换是全服务层回归；
  2. 本项目当前瓶颈在渲染层与缓存策略（已解决），不在请求次数——REST 分页接口每页已合并取数；
  3. 限流：REST 认证后 5000 req/h，当前场景余量充足。
- 启用条件（登记）：出现"单页 >3 次串行聚合请求"的场景（如仓库页首屏聚合）再评估。

### 2.2 HdsListItem 左滑 vs 原生 swipeAction

- 决策：本轮用原生 `ListItem.swipeAction`（@9 起稳定、参数化零开销）。
- HdsListItem 官方样式更贴 HDS 规范，但要求整行重构为 HdsListItem 卡片形态，涉及全部列表 id
  契约回归——登记 R13 候选。

### 2.3 五 Tab vs 官方 4 Tab

- 官方 App 实际 4 Tab（Home/Notifications/Explore/Profile，见 GitHub Blog 2026-03 changelog）；
  按目标规格实现 5 Tab，"代码"Tab = 全局搜索一级入口（能力对齐官方搜索，入口化）。

## 3. R12+ 补充结论（调研深化后更新）

### 3.1 SharedElementTransition（06 文档 §5.3 登记项 → 评估后不采用）

- SDK 提供 `geometryTransition(id)` @11（隐式共享元素，单 id 仅绑定两个组件、一进一出配对）。
- 不采用原因（可查证）：
  1. 本应用 Navigation push 转场时源/目标两个 NavDestination 同时在栈，不满足"一进一出"配对前提；
  2. 动态流中同一用户头像在多行重复出现，行级同 id 会互相冲突；
  3. 可行的替代是 `customNavContentTransition` 全自定义转场——需要重写全部页面转场，
     与"系统默认转场已对齐官方横滑手感"（03 文档 §1）的既定结论冲突。
- 重启条件：单点确定配对场景（如探索页卡片 → 仓库详情头图）单独评估。

### 3.2 通知推送与角标（R12+ 客户端闭环已落地）

- `notificationManager.setBadgeNumber` @9 **deprecated since 26.0.0**；
- 官方替代路径：发布通知时在 NotificationRequest 携带 `badgeNumber`——已落地：
  - `common/base/utils/NotificationUtil`：授权查询/申请（isNotificationEnabled +
    requestEnableNotification）+ `publishUnreadBadgeNotification`（BASIC_TEXT 内容 +
    badgeNumber = 未读数，重复发布覆盖同 id 通知不堆积）；
  - `NotifyViewModel.refresh` 真实数据刷新成功后 diff 未读（Preferences 持久化上次值），
    未读新增时发布系统通知并同步角标；boot 注入测试数据走独立分支不误报；批量已读清零；
- **分工边界**：应用前台/可见时的通知提醒与角标同步已客户端闭环；
  退后台实时推送仍需服务端推送通道（Push Kit + GitHub webhook 桥），作为服务端增强排期。
